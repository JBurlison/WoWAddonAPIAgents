# Put addon preferences in the client options menu

For new addons with configurable behavior, provide a discoverable category in the selected client's built-in addon settings menu. Apply this requirement when adding or changing preferences in existing addons. A slash command or standalone panel can supplement the menu entry; it should not be the only way to find ordinary preferences. A canvas category can host a custom editor or a clearly labeled launcher for a larger configuration window. Preserve explicit user scope decisions; record why an addon with no configurable behavior needs no category rather than inventing settings.

## Registration and lifetime

1. Resolve the clients and verify the loaded Settings owner, signatures and permissions at each task's source pin. Read [current settings contracts](CURRENT-SETTINGS.md) for the registration example and loading caveats. Function presence is only a readiness check after contract verification; do not guess an `InterfaceOptions_AddCategory` fallback from an older client.
2. Load the [localization table](../../wow-addon-development/references/LOCALIZATION.md) before constructing labels, tooltips, section names or errors. Keep setting variables, database keys and option values stable and unlocalized.
3. Initialize and migrate SavedVariables after the addon's own `ADDON_LOADED`. Decide account-wide versus per-character scope and validate stored types/ranges. Default only missing/invalid values; a saved `false` is intentional. Use SavedVariables for addon preferences and CVars only for actual client settings explicitly being changed.
4. Prefer `Settings.RegisterVerticalLayoutCategory(localizedName)` for standard controls; use `RegisterCanvasLayoutCategory(frame, localizedName)` when custom layout is warranted. Attach subcategories using the verified parent/category contracts. Register the root with `Settings.RegisterAddOnCategory(category)` **once**, not on every open or frame show.
5. Keep a category reference and open it with `Settings.OpenToCategory(category:GetID())` from a user action. Do not use a translated display name as its identity, persist session category IDs or automatically open the menu on login. Verify load-on-demand readiness and handle already-loaded owners as well as later loading.
6. `RegisterAddOnSetting(category, variable, variableKey, variableTbl, variableType, name, defaultValue)` binds to a specific table/key. Use namespaced variables and `setting:SetValueChangedCallback(function(setting, value) ... end)` for ordinary runtime updates. Apply the saved initial state separately; registering a callback does not prove it ran at initialization. `RegisterProxySetting` requires owned getter/setter/default initialization and is useful when adapting an existing database or profile system.
7. Define immediate versus Apply/reload-required behavior accurately. Canvas `OnCommit`, `OnDefault` and `OnRefresh` have their owner's semantics; do not assume legacy Okay/Cancel callbacks or promise automatic rollback. Synchronize menu and custom-panel values through the same setting/model. Preserve bound table identity when resetting/migrating; a profile switch must rebind through a supported path or use accessors that resolve the current profile.
8. Reset only this addon's requested scope, copy default tables instead of sharing mutable defaults, and refresh the visible controls and runtime state. Explain destructive resets where appropriate. Defer protected runtime changes during combat through the verified client path, keeping saved intent and actual applied state distinct. Do not perform forbidden work in a value-change callback.

Do not add a dependency on Ace3 or another configuration framework merely to expose options. If the addon already uses one, verify its target support, bridge category registration and load order, and package its required dependencies. Preserve the existing project architecture.

## Acceptance per selected client

- Discover the addon from the actual built-in settings/options menu, then open the same category through any addon shortcut. Check subcategories, repeated opening and late loading without duplicate entries or hooks.
- Change boolean, numeric and enumerated values as applicable; verify initial state, immediate/Apply semantics, defaults, invalid old data, external changes and profile switching. Check persistence through reload, logout/login and restart separately.
- Exercise mouse, keyboard and applicable [controller acquisition/navigation](../../wow-controller-support/SKILL.md), including modal return, focus, tooltips and scrolling. A native template alone does not establish controller support.
- Test translated category names, labels, help, reset confirmations and status messages; long strings and missing translations must remain usable. Keep [visual fidelity](../../wow-addon-development/references/VISUAL-FIDELITY.md) and the existing testing choice.
- Record missing registration capability per client, retain saved preferences, and document a verified reduced integration when necessary. Static registration code or a simulator menu is not proof of actual client discovery/persistence.
